# ClipShare i18n 规范

本文档用于约束 ClipShare 项目的国际化键命名、翻译文案、术语统一和维护方式。

目标：

- 保证翻译键清晰、稳定、易维护
- 保证中文开发体验顺手，同时兼顾英文文案长度带来的 UI 约束
- 保证代码、配置、文档、界面中的术语一致
- 保证废弃翻译能及时清理，不形成长期库存

## 1. 总体原则

- `TranslationKey` 表达的是“用途”，不是“翻译内容”
- 一个键只表达一个语义，不复用相近但不同的文案
- 中文可以作为主开发语言，但命名和布局要默认英文更长
- 长文案优先拆分，不把标题、说明、风险提示塞进同一个键
- 废弃键必须及时删除，不保留无引用库存

## 2. 翻译键命名规范

- 命名格式统一为：`模块/页面 + 对象/区域 + 语义`
- 推荐顺序固定为：`模块 -> 组件/对象 -> 类型`
- 键名应能直接表达“在哪用 + 是什么”
- 键名尽量控制在 `2 到 4 段`
- 不允许使用无语义名称，例如：
  - `text1`
  - `msg`
  - `labelText`
  - `value1`

推荐示例：

- `settingsSectionLanguageSubtitle`
- `devicePagePairingDialogTitle`
- `forwardSettingsForwardAddressDesc`

## 3. 后缀规范

统一使用以下后缀：

- 标题：`Title`
- 描述：`Desc`
- 输入提示：`Hint`
- 悬浮提示：`Tooltip`
- 弹窗正文：`DialogContent`
- 模板文案：`Template`
- 成功结果：`Success`
- 失败结果：`Failed`

补充规则：

- `Desc` 与 `Description` 不允许混用，统一只使用 `Desc`
- `Text` 仅作为兜底后缀，能用更明确后缀时优先不用 `Text`
- 不允许叠后缀，主后缀只保留一个
- 不再新增 `Ack` 相关命名，确认类语义统一使用 `Confirm` / `DialogContent` 等更直白的表达

## 4. 翻译值规范

- 标题短，描述清楚
- 按钮、Tab、菜单、设置项标题尽量使用短语，不写完整长句
- 中文优先自然表达，不做生硬直译
- 英文优先短而自然，不追求逐字对应，但不能删掉中文里的触发条件、限制条件、风险提示等业务含义
- 同一术语必须统一翻译，不允许同义词混用
- 同一类文案保持统一语气
  - 按钮：动作词
  - 描述：说明句
  - 提示：简短提醒
  - 错误：直接说明问题

补充规则：

- 英文应以中文为语义蓝本；缩短文案时优先调整句式、拆分信息，不直接删除关键含义
- 设置项标题优先使用稳定的名词短语或明确动作，避免动名词、动词短语、名词短语在同一组中随意混用
- 设置项描述必须保留“什么时候触发 / 影响什么 / 有什么风险”这类条件信息
- 平台名称大小写固定为 `Android`、`iOS`、`Linux`、`macOS`、`Windows`
- 操作按钮使用短动作词，例如 `Start`、`Select`、`Configure`；避免 `Start Up` 这类不自然表达
- 运行时默认展示名也要走翻译，例如本机、默认分组、统计图例等；避免英文界面混入中文兜底值
- 初始化早于 GetX 翻译注册的服务、配置、实体对象，不要直接调用 `.tr`；保留稳定存储值，在 UI 展示层通过 `displayName` / formatter 统一本地化

## 5. 文案长度规范

这里约束的是翻译值，不是键名长度。

建议规则：

- 按钮文案：尽量 `2 到 6` 个中文字，英文尽量 `1 到 3` 个词
- Tab / 菜单 / 分区标题：尽量短，不写解释句
- 设置项标题：一眼看懂，不堆额外说明
- 设置项副标题：可两行，但不要写成长段说明
- 设置分区副标题：只说明分区范围，不重复标题；如果英文超过两行，应先改文案再考虑 UI 样式
- 一级概览卡片的状态文字保持单行；版本号、协议、状态徽标等辅助信息优先放到独立区域，不用强制换行兜底
- Dialog 标题：尽量短
- Dialog 正文：优先控制在 `2 到 4` 行，过长必须拆段
- Tooltip：尽量一句短语

执行原则：

- 标题只放核心动作或核心概念
- 解释内容放 `Desc` / `Tooltip` / `DialogContent`
- 如果英文过长，优先拆文案结构，不优先缩字体
- 技术实现标记、类名、长常量名不应直接塞进设置页说明；面向用户时说明其业务含义，必要时再放到 Tooltip 或文档
- 说明文案如果会与右侧按钮、数值或可访问文本拼接，句尾不要强行加句号，避免出现 `..` 或读屏重复停顿
- 设备名这类既参与同步/存储又参与 UI 展示的字段，要区分原始值和展示值：原始字段用于协议、数据库和日志，展示字段用于页面、筛选器、统计和导出

补充说明：

- 如果界面只是提供一个“查看说明”的入口，翻译值可以直接使用“说明” / `Description`
- 但对应 key 仍然必须绑定到具体业务语义，不能只命名成泛化的 `description`

## 6. 术语统一规范

与中转服务相关术语固定如下：

- 英文统一使用 `forward`
- 中文统一翻译为“中转”

统一表达：

- `forward` = 中转
- `forward server` = 中转服务器
- `forward service` = 中转服务
- `forward mode` = 中转模式

补充规则：

- 不再使用 `relay`、`proxy`、`transfer` 等词指代同一能力，除非明确是不同概念
- 术语统一优先于局部最优表达
- 状态短语可使用 `&` 压缩固定并列概念，例如 `Auth & encryption`、`UI & interaction`；完整说明句中优先使用自然语法，不为了缩短滥用 `&`

## 7. 缩写规范

- 缩写必须克制使用
- 非必要不使用缩写，优先全称
- 缩写应采用固定白名单机制，禁止自由发挥
- 同一缩写大小写必须统一
- 不再新增拼写模糊或可读性差的缩写键

建议：

- 对已有 `Perm`、`Dev`、`Cfg` 等缩写逐步收敛
- 对平台名称大小写保持统一，不混用 `IOS` / `iOS` 等形式

## 8. 拼写规范

- 禁止新增拼写错误翻译键
- 新增 key 前必须检查拼写
- 已存在的错误命名视为历史包袱，不作为后续新增参考

当前项目中的典型反例：

- `addDeviceAppBarTittle`
- `newParingRequest`
- `paringRequest`
- `codePromptParamsContentSouce`
- `codePromptParamsContentTpye`
- `codePromptNotificationTpye`

## 9. 复用规范

可以复用的基础通用词：

- `confirm`
- `cancel`
- `save`
- `delete`
- `search`

不可强行复用的文案：

- “保存成功” 和 “更新成功”
- “删除记录” 和 “删除文件”
- “连接失败” 和 “发送失败”

规则：

- 不允许为了少建键而复用错误语义文案
- 泛义词如果不是全局通用键，必须带业务前缀

## 10. 结构拆分规范

优先采用以下结构：

- `Title`
- `Desc`
- `Tooltip` / `DialogContent`

规则：

- 不要让单个键同时承担操作名、说明、风险提示
- 如果一条文案同时包含“是什么 + 为什么 + 注意事项”，必须拆分
- 不要把实现细节写进 key，除非它本身就是业务概念

## 11. UI 约束

- 中文可以作为开发主环境，但 UI 需要按英文不溢出做兜底
- 单行区域必须预留英文长度余量
- 描述区域默认支持换行
- 不允许以“中文刚好能放下”作为布局基准

高风险位置必须重点走查：

- 按钮
- Tab
- AppBar 标题
- 设置项标题
- 菜单项
- Snackbar / Toast
- 卡片单行标题
- 弹窗按钮

## 12. 维护规范

- 新增翻译键时必须同时补中英文
- 翻译相关新增或实质修改的方法必须补中文方法注释
- 同模块翻译键尽量集中放置，并按功能分段
- 删除功能时必须同步删除废弃键和翻译分支
- 定期检查以下内容：
  - 未使用翻译键
  - 同义重复键
  - 后缀混用
  - 拼写错误
  - 英文过长文案
  - 术语不统一

## 13. 禁止项

- 禁止使用无语义键名
- 禁止 `Desc` / `Description` 混用
- 禁止主后缀叠加
- 禁止继续新增 `Ack` 命名
- 禁止将 `Tooltip` / `AppBar` / `Button` 等实现细节作为主要命名依据
- 禁止长说明塞进标题
- 禁止不同概念共用一个翻译键
- 禁止保留已无引用的废弃翻译键
- 禁止同一功能混用 `forward` 和 `relay`

## 14. 推荐执行口径

- 中文负责表达准确
- 英文负责长度校验
- UI 以英文不溢出为最低约束
- 术语以项目统一优先，不追求局部最优表达
